# Инструменты для лабораторных работ по C++

**Справочник студента** · «Программирование и алгоритмизация» (C++), 1 курс

В справочнике собраны все инструменты, которые понадобятся в лабораторных работах: терминал, компилятор, санитайзеры, отладчик, git, CMake, тестовый фреймворк doctest, clang-format и непрерывная интеграция. Для каждой команды указано, что она делает, а в начале раздела — с какой работы инструмент нужен. Читать подряд не обязательно: держите справочник открытым во время работы и возвращайтесь к нужному разделу.

**Обозначения.** Текст в угловых скобках (`<файл>`, `<имя>`) заменяется своим значением без скобок. Всё после `#` в строке команды — комментарий: набирать его не нужно, но если набрать, терминал его проигнорирует. Команды в примерах приведены для bash (Linux, WSL, macOS); отличия Windows собраны в разделе 3.6.

## 2. Установка окружения

Нужны: компилятор GCC 13 или новее (или Clang 17+), `gdb`, CMake 3.20+, `git`, по желанию `clang-format`, и редактор — VS Code или CLion.

### 2.1. Linux (Ubuntu, Debian) и WSL

```bash
sudo apt update                                                  # обновить список пакетов
sudo apt install build-essential gdb cmake git clang-format      # установить инструменты
```

| Команда | Что делает |
|---|---|
| `sudo apt update` | Обновляет список доступных пакетов. `sudo` выполняет команду с правами администратора и спрашивает пароль |
| `sudo apt install <пакеты>` | Устанавливает пакеты. `build-essential` — это `g++`, `make` и системные заголовки |
| `g++ --version` | Показывает версию компилятора (нужна 13 или новее) |
| `cmake --version` | Версия CMake (нужна 3.20 или новее) |
| `gdb --version`, `git --version` | Проверить, что отладчик и git установлены |

### 2.2. Windows

Рекомендуемый вариант — **WSL** (Windows Subsystem for Linux): полноценный Linux внутри Windows, в котором работают все инструменты курса, включая санитайзеры.

| Команда или действие | Что делает |
|---|---|
| `wsl --install` в PowerShell, запущенном от имени администратора | Устанавливает WSL и Ubuntu; после установки нужна перезагрузка |
| Запуск «Ubuntu» из меню «Пуск» | Открывает терминал Linux; при первом запуске нужно придумать имя пользователя и пароль |
| Команды из раздела 2.1 в этом терминале | Устанавливают инструменты курса внутри WSL |
| Расширение **WSL** в VS Code, затем `code .` в терминале Ubuntu | Открывает текущий каталог Linux в VS Code; компиляция и отладка идут внутри WSL |

Альтернатива — **MSYS2** (терминал «MSYS2 UCRT64»):

```bash
pacman -S mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-gdb mingw-w64-ucrt-x86_64-cmake git
```

`pacman -S` устанавливает пакеты в MSYS2. Ограничение: компилятор MinGW **не поддерживает санитайзеры**, поэтому начиная с ЛР 3 проверять решения придётся в WSL, в компьютерном классе или через CI.

### 2.3. macOS

| Команда | Что делает |
|---|---|
| `xcode-select --install` | Устанавливает инструменты разработчика Apple: компилятор Clang, git и отладчик lldb |
| `brew install cmake clang-format` | Устанавливает CMake и clang-format через менеджер пакетов Homebrew (brew.sh) |

На macOS команда `g++` на самом деле вызывает Clang — флаги те же. Вместо `gdb` используется `lldb` (соответствие команд — в разделе 6.6). Поиск утечек (LeakSanitizer) в Apple Clang не поддерживается.

### 2.4. Редакторы

**VS Code** — установить расширения: **C/C++** (Microsoft) — подсветка, автодополнение, отладка; **CMake Tools** — сборка CMake-проектов с ЛР 6; при работе в WSL — **WSL**.

**CLion** — открывает проекты с `CMakeLists.txt` без дополнительной настройки; для одиночных файлов ЛР 1–5 удобнее терминал.

## 3. Терминал

Используется с ЛР 1. Терминал — текстовый интерфейс к операционной системе: вы вводите команду, нажимаете Enter, система выполняет её и печатает результат.

### 3.1. Навигация и файлы

| Команда | Что делает |
|---|---|
| `pwd` | Показывает текущий каталог (где вы находитесь) |
| `ls` | Показывает содержимое текущего каталога |
| `ls -la` | Подробный список, включая скрытые файлы (имена с точки: `.gitignore`, `.git`) |
| `cd <каталог>` | Переходит в каталог |
| `cd ..` | Переходит на уровень выше |
| `cd ~` | Переходит в домашний каталог |
| `cd -` | Возвращается в предыдущий каталог |
| `mkdir <имя>` | Создаёт каталог |
| `mkdir -p lab06/src/include` | Создаёт всю цепочку вложенных каталогов сразу |
| `touch <файл>` | Создаёт пустой файл (у существующего обновляет время изменения) |
| `cp <откуда> <куда>` | Копирует файл |
| `cp -r <каталог> <куда>` | Копирует каталог со всем содержимым |
| `mv <откуда> <куда>` | Перемещает или переименовывает файл |
| `rm <файл>` | Удаляет файл **безвозвратно** — корзины в терминале нет |
| `rm -r <каталог>` | Удаляет каталог со всем содержимым; перед нажатием Enter проверьте путь дважды |

### 3.2. Просмотр и поиск

| Команда | Что делает |
|---|---|
| `cat <файл>` | Выводит файл целиком |
| `less <файл>` | Показывает файл постранично: пробел — следующая страница, `/текст` — поиск, `q` — выход |
| `head -n 5 <файл>` | Первые 5 строк файла |
| `tail -n 5 <файл>` | Последние 5 строк |
| `wc <файл>` | Число строк, слов и байтов в файле |
| `wc -l <файл>` | Только число строк |
| `grep "текст" <файл>` | Строки файла, содержащие текст |
| `grep -n "текст" <файл>` | То же с номерами строк |
| `grep -i "текст" <файл>` | Без учёта регистра |
| `grep -r "текст" .` | Поиск во всех файлах текущего каталога и подкаталогов |
| `sort <файл>` | Сортирует строки |
| `uniq -c` | Сворачивает подряд идущие одинаковые строки и считает их (обычно после `sort`) |
| `diff <файл1> <файл2>` | Показывает различия двух файлов; пустой вывод означает, что файлы совпадают |

### 3.3. Запуск программ, ввод и вывод

У каждой программы три стандартных потока: **ввод** (`stdin`, в C++ — `std::cin`), **вывод** (`stdout`, `std::cout`) и **поток ошибок** (`stderr`, `std::cerr`). По умолчанию ввод идёт с клавиатуры, а оба потока вывода — на экран. Терминал умеет перенаправлять их в файлы и в другие программы.

| Команда | Что делает |
|---|---|
| `./app` | Запускает программу `app` из текущего каталога. `./` обязателен: без него терминал ищет программу только в системных каталогах |
| `./app arg1 arg2` | Запускает программу с аргументами командной строки (`argc`/`argv`, с ЛР 10) |
| `./app < input.txt` | Подаёт файл на стандартный ввод вместо клавиатуры |
| `./app > out.txt` | Записывает стандартный вывод в файл (файл перезаписывается) |
| `./app >> out.txt` | Дописывает вывод в конец файла |
| `./app 2> err.txt` | Записывает поток ошибок в файл |
| `./app > out.txt 2>&1` | Записывает оба потока в один файл |
| `./app 2> /dev/null` | Выбрасывает сообщения об ошибках (`/dev/null` — «чёрная дыра») |
| `<команда1> \| <команда2>` | Конвейер: вывод первой команды становится вводом второй |
| `echo "2024" \| ./app` | Подаёт одну строку на вход программе |
| `printf '5\n3 1 2\n' \| ./app` | Подаёт несколько строк (`\n` — перевод строки) |
| `./gen > data.txt` | Сохраняет вывод генератора данных в файл |

Проверка программы на заранее подготовленном тесте:

```bash
./app < test1.txt > out.txt && diff out.txt expected1.txt && echo OK
```

Программа читает `test1.txt`, пишет ответ в `out.txt`, `diff` сравнивает его с эталоном; `OK` печатается, только если всё совпало.

### 3.4. Коды возврата, цепочки команд, замер времени

Число, которое возвращает `main`, — **код возврата**: 0 означает успех, любое другое значение — ошибку. Скрипты и системы CI определяют успех программы именно по нему.

| Команда | Что делает |
|---|---|
| `echo $?` | Печатает код возврата последней выполненной команды |
| `<a> && <b>` | Выполняет `b`, только если `a` завершилась успешно (код 0) |
| `<a> \|\| <b>` | Выполняет `b`, только если `a` завершилась с ошибкой |
| `<a> ; <b>` | Выполняет `b` в любом случае |
| `time ./app` | Запускает программу и печатает время: `real` — по часам, `user` — процессорное время самой программы, `sys` — время работы ядра системы на программу |

Код возврата 139 означает аварийное завершение по сигналу SIGSEGV («Segmentation fault») — обращение к чужой памяти или переполнение стека.

### 3.5. Полезные клавиши

| Клавиши | Что делает |
|---|---|
| Tab | Дополняет имя файла или команды; двойное нажатие показывает варианты |
| ↑ / ↓ | Листают историю введённых команд |
| Ctrl+R | Поиск по истории: начните набирать часть команды |
| Ctrl+C | Прерывает работающую программу (например, зациклившуюся) |
| Ctrl+D | Сообщает программе «конец ввода» (EOF) — так завершается цикл `while (std::cin >> x)` при вводе с клавиатуры |
| Ctrl+L или `clear` | Очищает экран |
| `history` | Показывает историю команд |
| `man <команда>`, `<команда> --help` | Справка по команде (выход из `man` — `q`) |

### 3.6. Отличия Windows

| Действие | bash (Linux, WSL, macOS) | PowerShell | cmd |
|---|---|---|---|
| Запустить программу | `./app` | `.\app.exe` | `app.exe` |
| Ввод из файла | `./app < in.txt` | `Get-Content in.txt \| .\app.exe` | `app.exe < in.txt` |
| Код возврата | `echo $?` | `$LASTEXITCODE` | `echo %ERRORLEVEL%` |
| Замер времени | `time ./app` | `Measure-Command { .\app.exe }` | — |
| Конец ввода с клавиатуры | Ctrl+D | Ctrl+Z, затем Enter | Ctrl+Z, затем Enter |

PowerShell не поддерживает оператор `<` и сообщает «The '<' operator is reserved for future use» — используйте `Get-Content` или cmd.

Если в консоли Windows вместо кириллицы видны «кракозябры», переключите кодировку консоли на UTF-8: в cmd — `chcp 65001`, в PowerShell — `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`. Надёжнее всего работать в WSL, где кодировка UTF-8 используется по умолчанию.

## 4. Компилятор g++

Используется с ЛР 1. Компилятор превращает исходный код в исполняемую программу в три этапа: **препроцессор** подставляет содержимое `#include` и раскрывает макросы, **компилятор** переводит каждый `.cpp` в машинный код (объектный файл `.o`), **компоновщик** (linker) собирает объектные файлы и библиотеки в одну программу. `clang++` принимает те же флаги, что и `g++`.

### 4.1. Строение команды

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -g main.cpp -o app
```

| Часть | Значение |
|---|---|
| `g++` | Вызов компилятора C++ |
| `-std=c++20` | Использовать стандарт языка C++20 |
| `-Wall -Wextra -Wpedantic` | Включить предупреждения |
| `-g` | Добавить отладочную информацию |
| `main.cpp` | Исходный файл (их может быть несколько) |
| `-o app` | Имя получившейся программы (без `-o` — `a.out`) |

### 4.2. Флаги

| Флаг | Что делает |
|---|---|
| `-std=c++20` | Выбирает стандарт языка |
| `-o <имя>` | Задаёт имя выходного файла |
| `-Wall` | Основной набор предупреждений: неиспользуемые переменные, неинициализированные значения, сомнительные условия |
| `-Wextra` | Дополнительные предупреждения: сравнение знаковых и беззнаковых чисел, неиспользуемые параметры и другие |
| `-Wpedantic` | Предупреждает о расширениях компилятора, которых нет в стандарте (например, массив переменной длины `int a[n]`) |
| `-Werror` | Превращает любое предупреждение в ошибку — программа не соберётся, пока предупреждения не исправлены |
| `-Wshadow` | Предупреждает, когда переменная скрывает другую с тем же именем (полезно, необязательно) |
| `-Wconversion` | Предупреждает о неявных преобразованиях с возможной потерей данных (`double` → `int`); даёт много сообщений, по желанию |
| `-g` | Добавляет отладочную информацию: имена переменных и номера строк для отладчика и отчётов санитайзеров |
| `-O0` | Без оптимизации (по умолчанию). Для отладки: код выполняется строка за строкой, как написан |
| `-O2` | Оптимизация. Для замеров времени: программа работает в разы быстрее |
| `-c` | Только компиляция в объектный файл `.o`, без компоновки |
| `-E` | Только препроцессор: печатает текст после подстановки `#include` |
| `-I <каталог>` | Добавляет каталог, в котором ищутся заголовки из `#include "..."` |
| `-D<ИМЯ>` | Определяет макрос, как `#define ИМЯ` в начале файла |
| `-DNDEBUG` | Отключает все `assert` — так собирают релизные версии |
| `-D_GLIBCXX_ASSERTIONS` | Включает проверку индексов в `operator[]` у `std::vector`, `std::string` и других контейнеров (только GCC) |
| `-fsanitize=address` | Включает AddressSanitizer (раздел 5) |
| `-fsanitize=undefined` | Включает UndefinedBehaviorSanitizer (раздел 5) |
| `-fsanitize=address,undefined` | Оба санитайзера сразу |
| `-fno-omit-frame-pointer` | Делает стеки вызовов в отчётах санитайзеров точнее |
| `-fno-sanitize-recover=all` | Останавливает программу на первой ошибке UBSan (по умолчанию UBSan печатает сообщение и продолжает работу) |

### 4.3. Типовые команды

| Задача | Команда |
|---|---|
| Обычная сборка | `g++ -std=c++20 -Wall -Wextra -Wpedantic -g main.cpp -o app` |
| Отладочная сборка с санитайзерами (с ЛР 3) | `g++ -std=c++20 -Wall -Wextra -g -fsanitize=address,undefined -fno-omit-frame-pointer main.cpp -o app` |
| Сборка для замеров времени (с ЛР 4) | `g++ -std=c++20 -Wall -Wextra -O2 main.cpp -o app` |
| Программа из нескольких файлов | `g++ -std=c++20 -Wall -Wextra main.cpp search.cpp -o app` |
| Тесты на doctest (с ЛР 4) | `g++ -std=c++20 -Wall -Wextra -g tests.cpp -o tests` |
| Заголовки лежат в другом каталоге | `g++ -std=c++20 -Wall -Wextra -I include -I third_party src/main.cpp src/search.cpp -o app` |

Раздельная компиляция — то, что делает CMake «под капотом» (ЛР 6):

```bash
g++ -std=c++20 -c search.cpp           # search.cpp → search.o
g++ -std=c++20 -c main.cpp             # main.cpp → main.o
g++ main.o search.o -o app             # компоновка в программу
```

### 4.4. Как читать сообщения компилятора

Сообщение имеет вид `файл:строка:колонка: тип: текст`. Тип `error` — ошибка, программа не собрана; `warning` — предупреждение; `note` — пояснение к предыдущему сообщению.

```
broken.cpp:5:33: error: expected ';' before 'std'
```

Правила: **исправляйте первую ошибку и пересобирайте** — остальные часто её следствие; читайте текст после слова `error`, а не только номер строки; если ошибка внутри стандартной библиотеки или шаблона (ЛР 9), ищите в длинном сообщении строку `required from here`, указывающую на ваш файл.

Ошибки компоновщика (этап после компиляции) распознаются по `ld` или `collect2: error: ld returned 1 exit status`:

| Сообщение | Причина | Что делать |
|---|---|---|
| `undefined reference to 'f(...)'` | Функция объявлена, но её определение не попало в сборку | Передать компилятору все `.cpp`; в CMake — добавить файл в `add_library`/`add_executable` |
| `multiple definition of 'f(...)'` | Тело функции оказалось в нескольких объектных файлах — обычно определение в заголовке | Перенести определение в `.cpp` или пометить функцию `inline` |
| `undefined reference to 'main'` | Собирается файл без функции `main` | Добавить файл с `main` или собирать только объектный файл (`-c`) |

## 5. Санитайзеры

Используются с ЛР 3 (UBSan показывается уже в ЛР 1). Санитайзер — режим сборки, при котором компилятор встраивает в программу проверки. Программа работает медленнее (примерно в 2 раза) и использует больше памяти, зато при ошибке сразу останавливается с точным отчётом.

### 5.1. Что они находят

| Санитайзер | Флаг | Находит |
|---|---|---|
| AddressSanitizer (ASan) | `-fsanitize=address` | Выход за границы массива в куче, на стеке и в глобальных переменных; использование памяти после освобождения; двойное освобождение; переполнение стека |
| LeakSanitizer (LSan) | включён в ASan на Linux | Утечки памяти — память, выделенную через `new`, не освободили |
| UndefinedBehaviorSanitizer (UBSan) | `-fsanitize=undefined` | Переполнение знаковых целых, деление на ноль, некорректные сдвиги, разыменование нулевого указателя и другое неопределённое поведение |

### 5.2. Названия ошибок в отчётах

| В отчёте | Что произошло |
|---|---|
| `heap-buffer-overflow` | Выход за границы памяти, выделенной в куче (`std::vector`, `new[]`) |
| `stack-buffer-overflow` | Выход за границы локального массива |
| `heap-use-after-free` | Обращение к уже освобождённой памяти (в том числе после перевыделения `std::vector`) |
| `attempting double-free` | Повторное освобождение одной и той же памяти |
| `stack-overflow` | Переполнение стека — обычно бесконечная или слишком глубокая рекурсия |
| `new-delete-type-mismatch` | Объект удалён через указатель на базовый класс без виртуального деструктора (ЛР 10) |
| `detected memory leaks` | Утечка: сколько байтов потеряно и где они были выделены |
| `runtime error: signed integer overflow` | Переполнение знакового целого (сообщение UBSan) |

### 5.3. Как читать отчёт

Пример — запись в шестой элемент вектора из пяти (ключевые строки, адреса сокращены):

```
==…==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x… at pc 0x… bp 0x… sp 0x…
WRITE of size 4 at 0x… thread T0
    #0 0x… in main out_of_bounds.cpp:10
0x… is located 0 bytes after 20-byte region [0x…,0x…)
    #8 0x… in main out_of_bounds.cpp:5
SUMMARY: AddressSanitizer: heap-buffer-overflow out_of_bounds.cpp:10 in main
```

Читать сверху вниз: **тип ошибки** (`heap-buffer-overflow`); **операция** (`WRITE of size 4` — запись 4 байтов, то есть одного `int`); **где** (строка `#0` — первая строка стека вызовов, указывающая на ваш файл: `out_of_bounds.cpp:10`); **чья память** (`0 bytes after 20-byte region` — сразу за концом блока из 20 байтов, то есть пяти `int`, который был выделен в строке 5). Номера строк видны, только если программа собрана с `-g`.

### 5.4. Настройка через переменные окружения

| Команда | Что делает |
|---|---|
| `UBSAN_OPTIONS=print_stacktrace=1 ./app` | UBSan печатает стек вызовов, а не только строку ошибки |
| `ASAN_OPTIONS=detect_leaks=0 ./app` | Временно отключает поиск утечек (например, чтобы сначала разобраться с другой ошибкой) |

### 5.5. Ограничения

Санитайзеры находят ошибки только в том коде, который действительно выполнился, — поэтому их запускают вместе с тестами. Они не работают с компилятором MinGW на Windows (используйте WSL, Linux или MSVC с ключом `/fsanitize=address`). Замеры времени в сборке с санитайзерами бессмысленны: замеряйте в сборке `-O2` без них.

## 6. Отладчик gdb

Используется с ЛР 2. Отладчик позволяет остановить программу в любом месте, выполнять её по одной строке и смотреть значения переменных. Программу для отладки собирают с `-g` и без оптимизации (`-O0`), иначе отладчик не знает строк исходника, а часть переменных будет «optimized out».

### 6.1. Запуск

| Команда | Что делает |
|---|---|
| `gdb ./app` | Загружает программу в отладчик (программа ещё не запущена) |
| `gdb --args ./app arg1 arg2` | То же, с аргументами командной строки |
| `gdb -tui ./app` | Режим с окном исходного кода над командной строкой |

### 6.2. Точки останова

| Команда | Сокращение | Что делает |
|---|---|---|
| `break <функция>` | `b` | Остановиться при входе в функцию: `break digit_sum` |
| `break <файл>:<строка>` | `b` | Остановиться перед выполнением строки: `break main.cpp:12` |
| `break <файл>:<строка> if <условие>` | | Условная точка останова: `break main.cpp:12 if i == 99` — удобно в длинных циклах |
| `tbreak <место>` | | Временная точка: срабатывает один раз |
| `info breakpoints` | `i b` | Список точек останова с номерами |
| `delete <номер>` | `d` | Удалить точку; `delete` без номера — удалить все |
| `disable <номер>`, `enable <номер>` | | Временно выключить и снова включить точку |

### 6.3. Выполнение

| Команда | Сокращение | Что делает |
|---|---|---|
| `run` | `r` | Запустить программу (до первой точки останова или до конца) |
| `run < input.txt` | | Запустить с вводом из файла |
| `run arg1 arg2 < input.txt` | | С аргументами и вводом из файла |
| `next` | `n` | Выполнить текущую строку, не заходя внутрь вызываемых функций (step over) |
| `step` | `s` | Выполнить текущую строку, заходя внутрь вызываемой функции (step into) |
| `finish` | | Выполнить функцию до конца и вернуться в вызывающую; печатает возвращённое значение (step out) |
| `until <строка>` | `u` | Выполнить до указанной строки — удобно, чтобы выйти из цикла |
| `continue` | `c` | Продолжить до следующей точки останова |
| Enter на пустой строке | | Повторить предыдущую команду (например, ещё один `next`) |
| `kill` | | Остановить программу, не выходя из отладчика |
| `quit` | `q` | Выйти из отладчика |

### 6.4. Просмотр данных и стек вызовов

| Команда | Сокращение | Что делает |
|---|---|---|
| `print <выражение>` | `p` | Значение переменной или выражения: `p n`, `p n % 10`, `p v`, `p v[2]`, `p *ptr`, `p ptr->next` |
| `print *arr@5` | | Пять элементов массива, на который указывает `arr` |
| `display <выражение>` | | Печатать значение автоматически после каждого шага; `undisplay <номер>` — отменить |
| `info locals` | `i lo` | Все локальные переменные текущей функции |
| `info args` | | Аргументы текущей функции |
| `set var <переменная> = <значение>` | | Изменить значение на лету, чтобы проверить гипотезу без пересборки |
| `watch <переменная>` | | Остановиться, когда переменная изменится — находит место, где «портится» значение |
| `backtrace` | `bt` | Стек вызовов: какая функция кого вызвала, с аргументами и строками |
| `frame <N>` | `f` | Перейти в кадр N стека, чтобы смотреть переменные вызывающей функции |
| `up`, `down` | | Перейти на кадр выше или ниже |
| `list` | `l` | Показать исходный код вокруг текущей строки |

### 6.5. Примеры

Поиск логической ошибки — программа считает сумму цифр, но для отрицательных чисел выдаёт 0:

```
$ gdb ./digit_sum
(gdb) break digit_sum
(gdb) run < input.txt
Breakpoint 1, digit_sum (n=123) at digit_sum_bug.cpp:5
(gdb) continue                 ← число 123 обрабатывается верно, переходим ко второму
Сумма цифр 123 = 6
Breakpoint 1, digit_sum (n=-123) at digit_sum_bug.cpp:5
5	    int sum = 0;
(gdb) next
6	    while (n > 0) {
(gdb) next
10	    return sum;          ← тело цикла не выполнилось ни разу
(gdb) print sum
$1 = 0
```

Поиск места аварийного завершения (`Segmentation fault`): запустить программу под отладчиком без точек останова — она остановится в момент ошибки — и выполнить `bt`. Верхняя строка стека, относящаяся к вашему файлу, и есть место ошибки.

```
(gdb) run < input.txt
Program received signal SIGSEGV, Segmentation fault.
(gdb) bt
```

### 6.6. lldb на macOS

| gdb | lldb | Что делает |
|---|---|---|
| `gdb ./app` | `lldb ./app` | Загрузить программу |
| `break main.cpp:12` | `b main.cpp:12` | Точка останова на строке |
| `break digit_sum` | `b digit_sum` | Точка останова на функции |
| `run` | `r` | Запустить |

| `next`, `step`, `finish` | `n`, `s`, `finish` | Шаги |

| `print n` | `p n` | Значение выражения |
| `info locals` | `frame variable` (или `v`) | Все локальные переменные |
| `watch x` | `watchpoint set variable x` | Остановка при изменении переменной |
| `bt` | `bt` | Стек вызовов |
| `quit` | `q` | Выйти |

## 7. Отладка в IDE

Отладчик IDE — это тот же `gdb` (или `lldb`) с графическим интерфейсом: точки останова ставятся щелчком слева от номера строки, переменные и стек вызовов видны в отдельных панелях.

### 7.1. VS Code

| Клавиша | Что делает |
|---|---|
| F9 | Поставить или снять точку останова на текущей строке |
| F5 | Начать отладку; во время остановки — продолжить (continue) |
| F10 | Следующая строка без захода в функции (step over) |
| F11 | Зайти внутрь вызываемой функции (step into) |
| Shift+F11 | Выйти из текущей функции (step out) |
| Shift+F5 | Остановить отладку |
| Ctrl+Shift+F5 | Перезапустить отладку |

Панели слева во время отладки: **Variables** — локальные переменные, **Watch** — выражения, которые вы добавили сами, **Call Stack** — стек вызовов (щелчок по кадру показывает его переменные), **Breakpoints** — список точек останова. Условная точка останова: правый щелчок по точке → «Edit Breakpoint» → условие, например `i == 99`.

Для одиночных файлов (ЛР 1–5) нужна конфигурация `.vscode/launch.json`. Программа должна быть заранее собрана с `-g`:

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Отладка app",
      "type": "cppdbg",
      "request": "launch",
      "program": "${workspaceFolder}/app",
      "args": ["<", "${workspaceFolder}/input.txt"],
      "cwd": "${workspaceFolder}",
      "MIMode": "gdb",
      "stopAtEntry": false
    }
  ]
}
```

| Поле | Значение |
|---|---|
| `program` | Путь к собранной программе |
| `args` | Аргументы; запись `"<", "файл"` подаёт файл на стандартный ввод (работает с gdb в Linux и WSL) |
| `cwd` | Рабочий каталог программы |
| `MIMode` | Отладчик: `gdb` (Linux, WSL, MSYS2) или `lldb` (macOS) |
| `stopAtEntry` | `true` — остановиться на первой строке `main` |

Для CMake-проектов (с ЛР 6) удобнее расширение **CMake Tools**: в строке состояния выбираются компилятор (kit), цель сборки и кнопки Build, Debug, Run.

### 7.2. CLion

CLion открывает каталог с `CMakeLists.txt` как проект и сам настраивает сборку и отладку.

| Клавиша (раскладка Windows/Linux) | Что делает |
|---|---|
| Ctrl+F8 | Поставить или снять точку останова |
| Shift+F9 | Запустить отладку |
| F8 | Следующая строка (step over) |
| F7 | Зайти в функцию (step into) |
| Shift+F8 | Выйти из функции (step out) |
| F9 | Продолжить (resume) |
| Ctrl+F2 | Остановить |

Ввод из файла: Run → Edit Configurations → поле «Redirect input from».

## 8. git

Используется с ЛР 1. git хранит историю изменений проекта: каждая сохранённая версия называется **коммитом**. Путь изменения: вы правите файлы в **рабочем каталоге** → командой `git add` отмечаете, что войдёт в следующий коммит (это **индекс**, или staging area) → `git commit` сохраняет снимок в локальную историю → `git push` отправляет коммиты в **удалённый репозиторий** (GitHub, GitLab), где их видит преподаватель.

### 8.1. Первоначальная настройка (один раз на компьютере)

| Команда | Что делает |
|---|---|
| `git config --global user.name "Иван Петров"` | Имя автора, которое попадёт в коммиты |
| `git config --global user.email "ivan@example.com"` | Почта автора (та же, что в аккаунте GitHub или GitLab) |
| `git config --global init.defaultBranch main` | Новые репозитории создаются с основной веткой `main` |
| `git config --global core.editor "code --wait"` | Редактор для сообщений коммитов — VS Code (по умолчанию — vim или nano) |
| `git config --list` | Показать текущие настройки |

Для отправки кода на GitHub по HTTPS вместо пароля используется токен доступа (Settings → Developer settings → Personal access tokens) либо SSH-ключ — инструкция есть в разделе помощи GitHub и GitLab.

### 8.2. Создание и получение репозитория

| Команда | Что делает |
|---|---|
| `git init` | Превращает текущий каталог в репозиторий (создаёт скрытый каталог `.git` с историей) |
| `git clone <адрес>` | Скачивает существующий репозиторий вместе со всей историей |
| `git remote add origin <адрес>` | Связывает локальный репозиторий с удалённым; `origin` — его общепринятое имя |
| `git remote -v` | Показывает, с какими удалёнными репозиториями связан локальный |
| `git branch -M main` | Переименовывает текущую ветку в `main` |
| `git push -u origin main` | Первая отправка ветки `main`; `-u` запоминает связь, дальше достаточно `git push` |

### 8.3. Ежедневный цикл

| Команда | Что делает |
|---|---|
| `git status` | Что изменилось, что добавлено в индекс, на какой вы ветке. Самая частая команда — выполняйте перед каждым коммитом |
| `git diff` | Построчные изменения, ещё не добавленные в индекс |
| `git diff --staged` | Изменения, уже добавленные в индекс (то, что войдёт в коммит) |
| `git add <файл>` | Добавить изменения файла в индекс |
| `git add lab03` | Добавить все изменения в каталоге |
| `git add .` | Добавить все изменения в текущем каталоге — сначала проверьте `git status`, чтобы не добавить лишнего |
| `git commit -m "lab03: решето Эратосфена"` | Сохранить коммит с сообщением |
| `git commit` | То же, сообщение пишется в редакторе (удобно для длинных сообщений) |
| `git push` | Отправить новые коммиты в удалённый репозиторий |
| `git pull` | Забрать изменения из удалённого репозитория (например, сделанные с другого компьютера) |

### 8.4. История

| Команда | Что делает |
|---|---|
| `git log` | Полная история коммитов (выход — `q`) |
| `git log --oneline` | Краткая история: одна строка на коммит |
| `git log --oneline --graph --all` | История всех веток в виде графа |
| `git show <хеш>` | Содержимое конкретного коммита; хеш — первые 7 символов из `git log --oneline` |
| `git log -p <файл>` | История изменений одного файла |

### 8.5. Отмена изменений

| Команда | Что делает |
|---|---|
| `git restore <файл>` | Вернуть файл к состоянию последнего коммита. Незакоммиченные изменения в нём **пропадут** |
| `git restore --staged <файл>` | Убрать файл из индекса; изменения в самом файле сохраняются |
| `git rm --cached <файл>` | Перестать отслеживать файл, оставив его на диске (например, случайно закоммиченный бинарник); `-r` — для каталога |
| `git commit --amend` | Исправить последний коммит: добавить забытый файл или поправить сообщение. Только если коммит ещё не отправлен |
| `git reset --soft HEAD~1` | Отменить последний коммит, оставив его изменения в индексе. Только для неотправленных коммитов |
| `git revert <хеш>` | Создать новый коммит, отменяющий указанный. Безопасно и для уже отправленных коммитов |
| `git stash` | Временно убрать незакоммиченные изменения, чтобы переключиться на другую задачу |
| `git stash pop` | Вернуть убранные изменения |

### 8.6. Ветки (с ЛР 8)

Ветка — независимая линия разработки. Работа над лабораторной ведётся в отдельной ветке и попадает в `main` только после ревью.

| Команда | Что делает |
|---|---|
| `git branch` | Список локальных веток; текущая отмечена `*` |
| `git branch -a` | Включая ветки удалённого репозитория |
| `git switch -c lab08` | Создать ветку `lab08` и перейти на неё |
| `git switch main` | Перейти на ветку `main` |
| `git push -u origin lab08` | Отправить новую ветку в удалённый репозиторий |
| `git merge lab08` | Влить ветку `lab08` в текущую |
| `git branch -d lab08` | Удалить ветку, уже влитую в текущую |
| `git fetch` | Скачать сведения об изменениях в удалённом репозитории, не меняя ваши файлы |

**Конфликт слияния** возникает, когда обе стороны изменили одни и те же строки. git помечает такое место в файле:

```
<<<<<<< HEAD
ваш вариант
=======
вариант из другой ветки
>>>>>>> lab08
```

Нужно отредактировать файл, оставив правильный вариант и удалив маркеры, затем выполнить `git add <файл>` и `git commit`.

### 8.7. Файл .gitignore

`.gitignore` в корне репозитория перечисляет файлы, которые git не должен отслеживать: результаты сборки, бинарники, настройки IDE.

```
# Сборка
build/
*.o
*.exe
*.out
app
# Файлы IDE
.vscode/
.idea/
```

| Запись | Значение |
|---|---|
| `build/` | Каталог `build` целиком |
| `*.o` | Все файлы с расширением `.o` |
| `app` | Файл с таким именем в любом каталоге |
| `!important.txt` | Исключение: этот файл отслеживать, даже если он попадает под другие правила |
| `# текст` | Комментарий |

`.gitignore` не действует на файлы, которые уже есть в репозитории: их сначала нужно убрать командой `git rm --cached`.

### 8.8. Сообщения коммитов

Формат в курсе: `labNN: что сделано`. Сообщение отвечает на вопрос «что изменилось и зачем» и понятно без просмотра кода.

| Хорошо | Плохо |
|---|---|
| `lab03: анализ датчика, скользящее среднее за O(n)` | `fix` |
| `lab05: исправлен выход за границы в merge` | `asdf` |
| `lab06: тесты для count_in_range на граничных интервалах` | `сделал лабу` |

Один коммит — одно логическое изменение. Коммитьте чаще: маленькие коммиты проще проверить и при необходимости отменить.

## 9. Merge request и код-ревью

Используется с ЛР 8. **Merge request** (в GitLab) или **pull request** (в GitHub) — запрос на слияние ветки с `main`, в котором другой человек проверяет код до того, как он попадёт в основную ветку.

**Порядок работы автора:**

1. `git switch main` и `git pull` — начать с актуальной версии.
2. `git switch -c lab08` — создать ветку для работы.
3. Писать код, коммитить: `git add`, `git commit`.
4. `git push -u origin lab08` — отправить ветку.
5. На сайте GitHub или GitLab нажать «Compare & pull request» или «Create merge request», указать ветку `lab08` → `main`, написать описание: что сделано, как проверить, что осталось нерешённым. Назначить ревьюера.
6. Ответить на каждый комментарий ревьюера: исправить код или объяснить, почему он верен. Исправления — обычными коммитами в ту же ветку и `git push`: merge request обновится сам.
7. После одобрения ревьюера (и зелёного CI с ЛР 10) нажать «Merge».

**Порядок работы ревьюера:** открыть вкладку изменений (Files changed / Changes), пройти по чек-листу курса и оставить комментарии к конкретным строкам. Хороший комментарий называет проблему и предлагает решение: «Здесь `i <= v.size()` выходит за границу на последней итерации — нужно `<`», а не «неправильно». Отделяйте обязательные замечания от пожеланий (например, начинайте пожелание со слова «предложение:»).

**Что проверять на ревью** (кратко по чек-листу курса): проект собирается по README без предупреждений; тесты проходят и покрывают граничные случаи; некорректный ввод обрабатывается; имена переменных и функций понятны; нет «магических чисел»; функции делают одно дело; поля классов закрыты; нет ручного `new`/`delete` вне классов-владельцев; санитайзеры молчат; в репозитории нет сгенерированных файлов.

## 10. CMake и ctest

Используются с ЛР 6. CMake по описанию проекта в файле `CMakeLists.txt` сам вызывает компилятор с нужными флагами и в нужном порядке: собирает библиотеку, программы и тесты, пересобирает только изменённые файлы. ctest запускает зарегистрированные тесты.

### 10.1. Команды

| Команда | Что делает |
|---|---|
| `cmake -S . -B build` | Настройка (конфигурация): читает `CMakeLists.txt` из текущего каталога (`-S .`) и готовит систему сборки в каталоге `build` (`-B build`). Повторять при изменении `CMakeLists.txt` обычно не нужно — CMake сделает это сам при сборке |
| `cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug` | Отладочная конфигурация: `-g`, без оптимизации |
| `cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release` | Конфигурация для замеров: `-O3`, без `assert` |
| `cmake -S . -B build-asan -DSANITIZE=ON` | Задать значение опции проекта (опция `SANITIZE` описана в разделе 10.3) |
| `cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON` | Создать `compile_commands.json` — по нему clangd в VS Code понимает флаги проекта |
| `cmake --build build` | Собрать все цели |
| `cmake --build build -j` | Собрать, используя все ядра процессора |
| `cmake --build build --target tests` | Собрать только цель `tests` |
| `cmake --build build --clean-first` | Удалить результаты прошлой сборки и собрать заново |
| `rm -rf build` | Полностью удалить каталог сборки — помогает при «странных» ошибках кеша CMake |
| `ctest --test-dir build` | Запустить все тесты, зарегистрированные через `add_test` |
| `ctest --test-dir build --output-on-failure` | То же, но при падении показать вывод теста (без этого ключа видно только «Failed») |
| `ctest --test-dir build -R unit` | Запустить только тесты, имя которых подходит под шаблон |
| `ctest --test-dir build -V` | Подробный вывод всех тестов |

Каталог `build` содержит только сгенерированные файлы и должен быть в `.gitignore`. Программы после сборки лежат в нём: `./build/app`, `./build/tests`.

В Windows с генератором Visual Studio тип сборки указывается при сборке, а не при настройке: `cmake --build build --config Release` и `ctest --test-dir build -C Release`.

### 10.2. Команды CMakeLists.txt

| Команда | Что делает |
|---|---|
| `cmake_minimum_required(VERSION 3.20)` | Минимальная версия CMake, с которой работает проект. Первая строка файла |
| `project(lab06 CXX)` | Имя проекта и язык (`CXX` — C++) |
| `set(CMAKE_CXX_STANDARD 20)` | Стандарт C++20 для всех целей |
| `set(CMAKE_CXX_STANDARD_REQUIRED ON)` | Ошибка, если компилятор не поддерживает C++20 (иначе CMake тихо возьмёт более старый стандарт) |
| `add_compile_options(-Wall -Wextra -Wpedantic)` | Флаги компиляции для всех целей проекта |
| `add_library(search src/search.cpp)` | Библиотека `search` из перечисленных файлов. Логика выносится в библиотеку, чтобы её подключали и программа, и тесты |
| `add_executable(app src/main.cpp)` | Исполняемая программа `app` |
| `target_include_directories(search PUBLIC include)` | Каталог заголовков цели. `PUBLIC` — каталог виден и самой библиотеке, и всем, кто её подключает; `PRIVATE` — только ей самой |
| `target_link_libraries(app PRIVATE search)` | Подключить библиотеку `search` к программе `app` |
| `target_compile_options(search PRIVATE -Wall)` | Флаги компиляции только для одной цели |
| `option(SANITIZE "описание" OFF)` | Опция проекта, которую можно включить при настройке: `-DSANITIZE=ON` |
| `if(SANITIZE) … endif()` | Условие |
| `add_link_options(-fsanitize=address)` | Флаги компоновки для всех целей (санитайзеры требуют их и при компиляции, и при компоновке) |
| `enable_testing()` | Включить поддержку ctest |
| `add_test(NAME unit COMMAND tests)` | Зарегистрировать тест `unit`, который запускает программу `tests`; тест пройден, если программа вернула код 0 |
| `message(STATUS "текст")` | Вывести сообщение при настройке — помогает при отладке `CMakeLists.txt` |

### 10.3. Типовой проект

```
lab06/
├── CMakeLists.txt
├── include/
│   └── search.h          объявления функций
├── src/
│   ├── search.cpp        реализация
│   └── main.cpp          программа: ввод, вызов функций, вывод
├── tests/
│   └── tests.cpp         тесты doctest
└── third_party/
    └── doctest/doctest.h
```

```cmake
cmake_minimum_required(VERSION 3.20)
project(lab06 CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
add_compile_options(-Wall -Wextra -Wpedantic)

option(SANITIZE "Сборка с AddressSanitizer и UBSan" OFF)
if(SANITIZE)
  add_compile_options(-fsanitize=address,undefined -fno-omit-frame-pointer)
  add_link_options(-fsanitize=address,undefined)
endif()

add_library(search src/search.cpp)
target_include_directories(search PUBLIC include)

add_executable(app src/main.cpp)
target_link_libraries(app PRIVATE search)

enable_testing()
add_executable(tests tests/tests.cpp)
target_include_directories(tests PRIVATE third_party)
target_link_libraries(tests PRIVATE search)
add_test(NAME unit COMMAND tests)
```

Две сборки рядом — обычная и с санитайзерами:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug && cmake --build build && ctest --test-dir build
cmake -S . -B build-asan -DSANITIZE=ON && cmake --build build-asan && ctest --test-dir build-asan --output-on-failure
```

### 10.4. Частые ошибки CMake

| Сообщение или симптом | Причина | Что делать |
|---|---|---|
| `The source directory ... does not appear to contain CMakeLists.txt` | Команда запущена не из каталога проекта | Перейти в каталог с `CMakeLists.txt` или указать путь в `-S` |
| `Cannot find source file: src/serch.cpp` | Опечатка в имени файла или файл не создан | Проверить имена в `add_library` и `add_executable` |
| `undefined reference to ...` при сборке | Файл `.cpp` не перечислен в цели или библиотека не подключена | Добавить файл в цель; добавить `target_link_libraries` |
| `fatal error: search.h: No such file or directory` | Каталог заголовков не указан | `target_include_directories` |
| Изменения не применились, непонятные ошибки после переименований | Устаревший кеш в `build` | `rm -rf build` и настроить заново |

## 11. doctest

Используется с ЛР 4. doctest — фреймворк модульного тестирования из одного заголовочного файла `doctest.h` (выдаётся в репозитории курса; исходный проект — github.com/doctest/doctest). Устанавливать ничего не нужно: файл кладут рядом с тестами или в `third_party/`.

### 11.1. Подключение

```cpp
#define DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN   // doctest сам создаст функцию main
#include "doctest.h"

#include "sorts.h"                          // тестируемый код

TEST_CASE("пустой массив") {
    std::vector<int> a;
    insertion_sort(a);
    CHECK(a.empty());
}
```

`#define DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN` пишется ровно в одном файле проекта и строго перед `#include "doctest.h"`. В этом файле не должно быть своей функции `main`.

### 11.2. Макросы

| Макрос | Что делает |
|---|---|
| `TEST_CASE("имя")` | Объявляет тест. Каждый тест выполняется независимо |
| `SUBCASE("имя")` | Подслучай внутри теста. Тест выполняется заново с начала для каждого подслучая — удобно, когда несколько проверок используют общую подготовку |
| `CHECK(выражение)` | Проверка; при провале тест **продолжается**, ошибка печатается |
| `REQUIRE(выражение)` | Проверка; при провале тест **прекращается** — для условий, без которых дальнейшие проверки бессмысленны, и для циклов стресс-тестов |
| `CHECK_FALSE(выражение)` | Проверка, что выражение ложно |
| `CHECK_EQ(a, b)` | Проверка равенства; при провале печатает оба значения |
| `CHECK_THROWS(выражение)` | Проверка, что выражение бросает исключение (ЛР 8) |
| `CHECK_THROWS_AS(выражение, тип)` | Проверка, что бросается исключение конкретного типа: `CHECK_THROWS_AS(v.at(10), std::out_of_range)` |
| `CHECK_NOTHROW(выражение)` | Проверка, что исключения нет |
| `INFO("вход: " << x)` | Сообщение, которое печатается **только при провале** следующих проверок — например, входные данные стресс-теста |
| `CAPTURE(x)` | То же для одной переменной: при провале печатается `x := значение` |
| `MESSAGE("текст")` | Напечатать сообщение всегда |
| `FAIL("текст")` | Принудительно провалить тест |
| `doctest::Approx(0.3)` | Сравнение вещественных чисел с допуском: `CHECK(0.1 + 0.2 == doctest::Approx(0.3))` |

Каждый макрос `CHECK` и `REQUIRE` в отчёте называется «assertion»: строка `assertions: 6024 | 6024 passed` означает, что выполнено 6024 проверки.

Значения `std::vector` doctest печатает как `{?}`. Чтобы при провале видеть содержимое, добавьте собственную функцию преобразования в строку и выведите её через `INFO`.

### 11.3. Запуск и параметры

| Команда | Что делает |
|---|---|
| `./tests` | Запустить все тесты; код возврата 0 — все прошли |
| `./tests -s` | Печатать и успешные проверки (`--success`) |
| `./tests -tc="*сортир*"` | Запустить только тесты, имя которых подходит под шаблон (`--test-case`); `*` — любые символы |
| `./tests -tce="стресс*"` | Исключить тесты по шаблону (`--test-case-exclude`) |
| `./tests -sc="пустой"` | Запустить только подходящие подслучаи (`--subcase`) |
| `./tests -ltc` | Показать список тестов, не запуская их (`--list-test-cases`) |
| `./tests -aa=1` | Остановиться после первой проваленной проверки (`--abort-after`) |
| `./tests -d` | Показать время выполнения каждого теста (`--duration`) |
| `./tests -m` | Печатать только провалы (`--minimal`) |
| `./tests -nc` | Без цвета — для сохранения вывода в файл (`--no-colors`) |
| `./tests --help` | Список всех параметров |

Имена тестов с пробелами и кириллицей берут в кавычки; шаблоны по умолчанию не учитывают регистр.

## 12. clang-format

Рекомендуется с ЛР 6. clang-format автоматически оформляет код по заданным правилам: отступы, пробелы, переносы строк, расположение скобок. Код становится единообразным, а на ревью не приходится спорить о пробелах.

| Команда | Что делает |
|---|---|
| `clang-format -i main.cpp` | Отформатировать файл на месте (`-i` — записать результат в тот же файл) |
| `clang-format -i src/*.cpp include/*.h tests/*.cpp` | Отформатировать все файлы проекта |
| `clang-format main.cpp` | Напечатать отформатированный текст, не меняя файл |
| `clang-format --dry-run --Werror main.cpp` | Только проверить: при отличиях от правил — сообщения и ненулевой код возврата (подходит для CI) |
| `clang-format --style=Google --dump-config > .clang-format` | Создать файл настроек на основе готового стиля |

Настройки лежат в файле `.clang-format` в корне репозитория; clang-format находит его сам. Пример:

```yaml
BasedOnStyle: Google
IndentWidth: 4
ColumnLimit: 100
```

| Строка | Значение |
|---|---|
| `BasedOnStyle: Google` | Взять за основу стиль Google (другие варианты: `LLVM`, `Chromium`, `Mozilla`, `WebKit`, `Microsoft`) |
| `IndentWidth: 4` | Отступ — 4 пробела |
| `ColumnLimit: 100` | Максимальная длина строки — 100 символов |

Участок, который нельзя переформатировать (например, выровненная вручную таблица), обрамляют комментариями `// clang-format off` и `// clang-format on`.

В редакторе: VS Code — команда «Format Document» (Shift+Alt+F в Windows, Ctrl+Shift+I в Linux), автоматически при сохранении — настройка `"editor.formatOnSave": true`; CLion — Ctrl+Alt+L, использование `.clang-format` включается в Settings → Editor → Code Style.

## 13. Непрерывная интеграция (CI)

Используется с ЛР 10. CI — сервер, который при каждом `git push` сам скачивает репозиторий, собирает проект и запускает тесты. Результат виден на сайте: зелёная галочка — всё прошло, красный крестик — сборка или тесты упали. Merge request с красным CI в курсе не принимается.

### 13.1. GitHub Actions

Файл `.github/workflows/ci.yml` в репозитории:

```yaml
name: ci
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: cmake -S . -B build -DSANITIZE=ON
      - run: cmake --build build
      - run: ctest --test-dir build --output-on-failure
```

| Строка | Значение |
|---|---|
| `name: ci` | Название сценария, видно на вкладке Actions |
| `on: [push, pull_request]` | Когда запускать: при каждом push и при каждом pull request |
| `jobs:` → `build:` | Задание с именем `build` |
| `runs-on: ubuntu-latest` | Запускать на чистой виртуальной машине с Ubuntu; g++ и CMake там уже установлены |
| `steps:` | Шаги, выполняемые по порядку; если шаг завершился с ненулевым кодом, задание считается проваленным |
| `uses: actions/checkout@v4` | Готовое действие: скачать код репозитория |
| `run: <команда>` | Выполнить команду в терминале — те же команды, что вы запускаете у себя |

Результаты — на вкладке **Actions** репозитория и в самом pull request; щелчок по упавшему шагу показывает его вывод.

### 13.2. GitLab CI

Файл `.gitlab-ci.yml` в корне репозитория:

```yaml
build-and-test:
  image: gcc:13
  before_script:
    - apt-get update && apt-get install -y cmake
  script:
    - cmake -S . -B build -DSANITIZE=ON
    - cmake --build build
    - ctest --test-dir build --output-on-failure
```

| Строка | Значение |
|---|---|
| `build-and-test:` | Имя задания |
| `image: gcc:13` | Docker-образ, в котором выполняется задание: Linux с GCC 13 |
| `before_script:` | Подготовка: установить CMake, которого нет в образе |
| `script:` | Команды сборки и тестов; ненулевой код возврата любой из них проваливает задание |

Результаты — в разделе **Build → Pipelines** и в самом merge request.

## 14. cppreference.com

Основной справочник по языку C++ и стандартной библиотеке (en.cppreference.com; русская версия ru.cppreference.com заметно отстаёт — пользуйтесь английской). Быстрее всего искать через поисковик: «cppreference std::lower_bound».

Как читать страницу на примере `std::lower_bound`:

| Раздел страницы | Что из него узнать |
|---|---|
| Заголовок `Defined in header <algorithm>` | Какой `#include` нужен |
| Список сигнатур с номерами (1), (2), … | Варианты вызова; пометки `(since C++20)` и `(until C++17)` — с какого и до какого стандарта вариант доступен |
| Parameters | Что означает каждый параметр и какие у него требования (например, диапазон должен быть отсортирован) |
| Return value | Что возвращается — в том числе в особых случаях («если такого элемента нет — `last`») |
| Complexity | Сложность — важно для выбора контейнера и алгоритма (ЛР 12) |
| Exceptions | Какие исключения возможны |
| Possible implementation | Как функцию можно реализовать — полезно сравнить со своей реализацией |
| Example | Готовый пример с выводом; его можно запустить прямо на странице |

## 15. Шпаргалка: полный цикл работы над лабораторной

### ЛР 1–5: одиночные файлы

```bash
cd prog-labs                                   # репозиторий курса
git pull                                       # забрать изменения, если работали с другого компьютера
mkdir lab03 && cd lab03                        # каталог новой работы
code sensor.cpp                                # написать код (или открыть в любом редакторе)

g++ -std=c++20 -Wall -Wextra -Wpedantic -g sensor.cpp -o sensor                  # сборка
./sensor < sensor.txt                                                             # запуск на данных
g++ -std=c++20 -Wall -Wextra -g -fsanitize=address,undefined sensor.cpp -o sensor # проверка санитайзерами
./sensor < sensor.txt
```

## 16. Частые проблемы и их решения

| Симптом | Причина | Решение |
|---|---|---|
| `g++: command not found` | Компилятор не установлен или терминал не тот | Установить по разделу 2; в MSYS2 работать в терминале «MSYS2 UCRT64» |
| `./app: No such file or directory` | Программа не собрана или вы в другом каталоге | `pwd`, `ls`, пересобрать |
| `Permission denied` при запуске `./app` | У файла нет права на выполнение (часто после копирования из Windows) | `chmod +x app` |
| Программа ничего не делает после ввода | Она ждёт продолжения ввода — читает до конца ввода | Ctrl+D (Linux, macOS), Ctrl+Z и Enter (Windows) или подать файл через `<` |
| Вместо кириллицы «кракозябры» (Windows) | Кодировка консоли не UTF-8 | `chcp 65001` в cmd или работа в WSL |
| `fatal error: doctest.h: No such file or directory` | Файл не рядом с тестами и каталог не указан | Положить `doctest.h` рядом или добавить `-I <каталог>` |
| `undefined reference to ...` | Не передан `.cpp` с определением функции | Добавить файл в команду сборки или в цель CMake |
| `multiple definition of ...` | Определение функции в заголовке | Перенести в `.cpp` или пометить `inline` |
| Ошибка компоновки с `-fsanitize=address` в MinGW | MinGW не поддерживает санитайзеры | Проверять в WSL или Linux |
| `Segmentation fault` | Обращение к чужой памяти или переполнение стека | Собрать с `-g -fsanitize=address` и запустить или запустить в `gdb` и выполнить `bt` |
| gdb: `No symbol table is loaded` | Программа собрана без `-g` | Пересобрать с `-g` |
| gdb: `<optimized out>` вместо значения | Программа собрана с оптимизацией | Пересобрать с `-O0` |
| Замер показывает 0 мс или сильно скачет | Слишком мало данных, сборка `-O0`, фоновые программы | Увеличить n, собрать с `-O2`, повторить замер несколько раз |
| git: `rejected ... (fetch first)` при push | На сервере есть коммиты, которых нет у вас | `git pull`, при конфликте разрешить его, затем `git push` |
| git: `CONFLICT (content)` | Одни и те же строки изменены в двух местах | Раздел 8.6: отредактировать файл, `git add`, `git commit` |
| В репозиторий попали бинарники или `build/` | Не было `.gitignore` | Дополнить `.gitignore`, затем `git rm -r --cached build` и коммит |
| git: `Please tell me who you are` | Не настроены имя и почта | Раздел 8.1 |
| CMake: изменения не применились | Устаревший кеш | `rm -rf build` и настроить заново |
| PowerShell: `The '<' operator is reserved for future use` | PowerShell не поддерживает `<` | `Get-Content in.txt \| .\app.exe` или cmd |
